# Roadmap TrafficLens

Документ фиксирует ближайшие релизы. Приоритет — ценность для расследования и эксплуатации на одном хосте/площадке, без преждевременного усложнения в кластер.

## 0.2.0 — отчёт и стабилизация

Статус: в работе, основная часть уже в `main`.

Состав:

- приоритетные хосты на сводке отчёта;
- исправленные и более понятные причины скорингового вердикта;
- серверный smoke-тест `tools/smoke_server.sh`;
- единая retention-политика, auth hardening, статус Suricata, SHA256 PCAP на ingest.

Критерии выпуска:

- `python3 -m pytest -q` — зелёный;
- `bash tools/smoke_server.sh` на сервере — `SMOKE OK`;
- CHANGELOG и `docs/` отражают поведение;
- образ собирается и проходит healthcheck после `systemctl --user restart trafficlens`.

## 0.3.0 — расследование

Цель: сократить время от вердикта до понимания «что случилось и кого трогать».

Задачи:

1. **Карточка хоста/инцидента** — сделано в 0.2.0 (страница `/jobs/<id>/host/<ip>`: таймлайн, контакты, IOC, файлы); осталось:
   - ~~кнопки перехода в отфильтрованные вкладки отчёта~~ — сделано в 0.2.0 (кнопки ↗ в карточке хоста открывают вкладку отчёта с применённым фильтром `?flt=`).

2. **Цепочка компрометации** — сделано в 0.2.0: страница `/jobs/<id>/chain` (находки по этапам ATT&CK в хронологии, хосты на нескольких этапах) и готовые текстовые цепочки для тикета `хост → индикатор → адрес:порт → файл → хэш → источники IOC`; осталось:
   - ~~показ уверенности: что факт из логов, что вывод эвристики~~ — сделано в 0.2.0 (бейджи «Факт»/«Эвристика» в причинах вердикта, риске хостов и заголовках разделов; в цепочке — показать так же).

3. **Разметка аналитиком** — сделано в 0.2.0:
   - статусы находок `confirmed` / `false_positive` / `ignored` (кнопка ⋯ в таблицах отчёта);
   - allowlist для ложных IOC/сигнатур/эвристик — глобальный, управление на странице «Индикаторы и правила»;
   - влияние на score: размеченные и allowlist-находки не дают очков вердикту и риску хостов, отчёт пересобирается автоматически.

4. **Экспорт и поиск**
   - CSV-экспорт IOC-хитов, файлов, алертов, приоритетных хостов — сделано в 0.2.0 (UTF-8 с BOM, открывается в Excel/LibreOffice); полный JSON-отчёт уже доступен кнопкой в шапке;
   - поиск по задачам: filename, хост, IOC, вердикт, дата, источник — сделано в 0.2.0.

Критерии готовности:

- из сводки можно за 1–2 клика перейти к доказательствам по хосту;
- у critical-задачи есть готовая текстовая цепочка для тикета;
- false-positive не даёт тот же score после пересверки;
- экспорт открывается в Excel/LibreOffice без ручной правки.

## 0.4.0 — эксплуатация и интеграции

Цель: сделать TrafficLens удобным для постоянной работы, а не только разового разбора.

Задачи:

1. **Наблюдаемость**
   - `trafficlens doctor`: версии движков, правила, IOC, место на диске, права на `/data`, очередь, retention;
   - `/metrics` для Prometheus: jobs, errors, analysis duration, IOC freshness, rules age, queue depth.

2. **Уведомления**
   - webhook/Telegram/Matrix при `critical`;
   - шаблон сообщения: вердикт, score, хосты, IOC, ссылка на отчёт.

3. **Доступ и аудит**
   - OIDC/LDAP/локальные пользователи;
   - роли: viewer / analyst / admin;
   - audit log: вход, удаление, rematch, правка custom IOC, смена конфигурации;
   - persistent rate-limit для `/login` в БД вместо памяти процесса.

4. **Надёжность данных**
   - backup/restore каталога данных;
   - проверка целостности `trafficlens.db`;
   - безопасная миграция схемы БД при обновлениях.

5. **Интеграции**
   - выгрузка подтверждённых IOC обратно в MISP/OpenCTI;
   - отправка критичных событий в Graylog/OpenSearch;
   - optional export блокировок для firewall/EDR.

Критерии готовности:

- админ видит состояние системы одной командой `trafficlens doctor`;
- critical-задача приходит в уведомление быстрее, чем аналитик открыл UI;
- действия пользователей трассируются;
- restore из backup проверен на тестовом каталоге.

## Принципы

- Сначала доказуемость находок, потом красота.
- Никаких изменений в боевой базе IOC ради демо.
- Каждая эвристика должна объяснять, почему она сработала.
- Быстрые проверки — локально/в CI, реальная проверка — `tools/smoke_server.sh` на сервере.
